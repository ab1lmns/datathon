# FastAPI для Forte Видеоконтроль

Базовый API для существующего React-фронтенда и контракта Datathon 26.
Реализованы загрузка MOV, проверка ключа, очередь задач, хранение статусов,
проверка контейнера через FFprobe и обработка в отдельном процессе.
Модель ещё не подключена: корректный MOV завершает задачу со статусом `failed`
и сообщением «Модель анализа пока не подключена». Сервис не выдаёт фиктивных вердиктов.

## Локальный запуск

Нужны Python 3.12+ и FFmpeg с FFprobe. Поддерживаются macOS и Linux.
На текущем компьютере окружение `.venv` и `.env` уже подготовлены.

```bash
cd backend
source .venv/bin/activate
python -m app
```

API: http://127.0.0.1:8000, Swagger UI: http://127.0.0.1:8000/docs,
OpenAPI: http://127.0.0.1:8000/openapi.json, состояние: http://127.0.0.1:8000/health.
`/health` сообщает работоспособность API и отдельно `analysis_available: false`.

Установка на новой машине:

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.lock
cp .env.example .env
python -c 'import secrets; print(secrets.token_urlsafe(32))'
```

Записать полученный ключ в `FORTE_API_KEY` в `.env`. Образец ключа не принимается.
FFmpeg устанавливается отдельно: `brew install ffmpeg` на macOS либо
`sudo apt-get install ffmpeg` на Debian/Ubuntu. Веса моделей и ML-библиотеки
будут добавлены после выбора модели и оборудования.

## Подключение фронтенда

Запустить `npm run dev` из `frontend`. В «Как это работает» → «Настройки подключения»
выбрать **API**, адрес `http://127.0.0.1:8000`, ключ из `backend/.env`.
Ключ вводится в UI и хранится только в памяти вкладки. Не добавлять его в `VITE_*`.
Фронтенд по умолчанию остаётся в демо-режиме; режим выбирается явно.
В Swagger нажать **Authorize** и ввести тот же ключ.

## Контракт API

Оба `/api/v1/*` endpoint требуют заголовок `X-API-Key`.

| Метод | Путь | Результат |
|---|---|---|
| POST | `/api/v1/analyze` | Multipart-поле `file`, MOV до 250 МиБ; HTTP 202 с `job_id` |
| GET | `/api/v1/jobs/{job_id}` | `processing`, `done` или `failed` |

```bash
read -r -s FORTE_TEST_KEY
export FORTE_TEST_KEY
curl http://127.0.0.1:8000/api/v1/analyze \
  -H "X-API-Key: $FORTE_TEST_KEY" -F 'file=@/path/to/video.mov'
curl http://127.0.0.1:8000/api/v1/jobs/JOB_ID \
  -H "X-API-Key: $FORTE_TEST_KEY"
unset FORTE_TEST_KEY
```

Ожидание: `{"job_id":"…","status":"processing"}`.
Ошибка: `{"job_id":"…","status":"failed","error":"Понятная причина"}`.
Успешный ответ после подключения модели:

```json
{
  "job_id": "…",
  "status": "done",
  "verdict": "no_violation",
  "violations": []
}
```

Для `violation` список непустой. У каждого события: `type`, `timecode_sec`,
`description`, от 1 до 3 `evidence_frames` с `timestamp_sec` и `image_base64`.
JPEG передаётся без префикса `data:`. Поле `rule` поддерживает `document`,
`section`, `url`; обработчик требует источник у каждого события, поскольку это
требование продукта, хотя минимальный JSON-пример жюри его не содержит.

Ошибки запроса: 401 — ключ; 404 — задача не найдена; 408 — загрузка превысила время;
413 — размер; 415 — расширение; 422 — отсутствующий/пустой файл; 429 — очередь заполнена.
Повреждённый MOV принимается как задача, затем получает `failed` после проверки FFprobe.
FFprobe проверяет контейнер, видеопоток и длительность; полное декодирование всех кадров
пока не выполняется. Отмена на фронтенде прекращает опрос, но не серверную обработку.

## Устройство и ограничения

- `app/main.py`: маршруты, загрузка, CORS, жизненный цикл.
- `app/middleware.py`: проверка ключа до чтения тела, лимит тела и времени загрузки.
- `app/storage.py`: SQLite, атомарное занятие задачи, сохранение и удаление результатов.
- `app/worker.py`: последовательная очередь и запуск отдельного процесса на задачу.
- `app/process_job.py`: FFprobe, вызов анализатора, проверка результата, удаление видео.
- `app/analyzer.py`: место подключения локальной модели.
- `app/schemas.py`: типы Pydantic, соответствующие `frontend/src/api/types.ts`.

Один API-процесс на каталог данных; блокировка не позволяет случайно запустить второй.
В API статусы ожидания в очереди и обработки представлены как `processing`.
По умолчанию допускается 4 незавершённые задачи, анализируется одна за раз.
Лимит 270 секунд отсчитывается от начала HTTP-запроса, включая загрузку и очередь.
По истечении времени процесс анализа и его дочерние процессы принудительно завершаются.
Попадание в очередь не гарантирует успешный анализ за 5 минут; это нужно измерить
на реальной модели и при необходимости уменьшить очередь.

После штатного завершения задачи исходный MOV удаляется. После аварии остаточные файлы
убирает фоновая очистка. Статусы и кадры результата хранятся 24 часа, затем удаляются
в течение следующего цикла очистки (обычно до минуты, если анализатор свободен).
Настройки хранения ограничены рамками кейса: после хакатона удалить локальные данные.
Задачи, выполнявшиеся при остановке, получают `failed`; очередь сохраняется и после
перезапуска обрабатывается, если не истёк её срок. История пользователя не реализована.

Ключ и `.env` не коммитятся. `data/`, видео и SQLite также исключены из Git.
На публичном сервере нужны HTTPS/reverse proxy, ограничение размера запроса на прокси
с запасом под multipart и явные разрешённые origin. Для доступа извне задать
`FORTE_HOST=0.0.0.0`. Публичное развёртывание этим изменением не выполняется.

## Подключение модели и требования кейса

Заменить `analyze_video` в `app/analyzer.py`: функция получает путь к видео и длительность,
возвращает `AnalysisResult`. Кадры должны извлекаться из исходного файла, таймкоды должны
попадать внутрь видео, названия правил и ссылки — приходить из проверенного справочника.
Модель обязана анализировать последовательность действий; отдельный кадр не всегда
подтверждает событие или отсутствие обязательного действия.

Обработка полностью локальная после предварительной загрузки весов. Запрещены облачные
AI API, отправка им видео/кадров/описаний, анализ звука и идентификация лиц.
Нельзя подменять анализ сопоставлением имени файла с разметкой. Разрешены только два
успешных вердикта; сбой модели и невозможность обработки дают `failed`.
Нормативные источники нужно исследовать отдельно и связать с наблюдаемыми действиями.
Классы событий и качество модели этим базовым API не определяются.

Сейчас процесс создаётся для каждой задачи. После выбора большой модели понадобится
постоянный процесс с заранее загруженными весами, проверка готовности модели и замеры
времени. Факт готовности API не означает выполнение AI-части кейса.

## Проверки

```bash
python -m pytest -q
ruff check .
```

Тесты используют синтетические видео, проверяют ключ, контракт, CORS, размер,
очередь, сохранение статусов, повреждённые видео, отсутствие модели и остановку процесса
по таймауту. Ответы `done` проверяются тестовыми данными, а не работающей моделью.

Основа реализации: [файлы в FastAPI](https://fastapi.tiangolo.com/tutorial/request-files/),
[жизненный цикл](https://fastapi.tiangolo.com/advanced/events/),
[отдельные процессы для тяжёлых задач](https://fastapi.tiangolo.com/tutorial/background-tasks/).
